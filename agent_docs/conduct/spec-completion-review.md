# Conduct checklist — /flow-next:spec-completion-review

A correct run resolves one review backend, has that backend verify the combined implementation of a spec's tasks against the spec's requirements, fixes what the verdict shows is wrong, and records the terminal completion status exactly once.

- [ ] Backend detection runs once — a single `flowctl review-backend` call (or an explicit `--review=` override) resolves the backend, and only that backend's `workflow-<backend>.md` enters context. Each review command runs as one blocking foreground call with a long timeout, never backgrounded and polled.
- [ ] The verdict comes from the backend's response, not the coordinator. A SHIP declared without a backend verdict, or a review the coordinator performed itself, has broken this. A backend failure prints `RETRY: no verdict (backend or transport failure)` and stops.
- [ ] Findings are spec-compliance gaps — requirements that never became tasks, requirements split incompletely across tasks, scope drift, missing doc updates — not code-quality notes, which belong to impl-review.
- [ ] A NEEDS_WORK verdict is followed by fixes, focused tests, a commit, and a re-review in the same session or chat, without asking the user; which findings are fixed and which become follow-ups follows the working rules' Review section. A delivered verdict is never re-framed as a transport failure to reclaim a round, and the reviewer sandbox is never widened.
- [ ] The terminal status is written once through the shared checkpoint — SHIP → `ship` and exit 0, capped NEEDS_WORK → `needs_work` with `ESCALATE:` and exit 4, NEEDS_HUMAN → `needs_human` with `ESCALATE:` and no further reserve or dispatch.
- [ ] A spec carrying `completion_review_status=not_required` reads as requirement-satisfied without a review having run — not `ship`, not `unknown` — and the skill never writes `not_required` itself (that write belongs to work's single-task policy skip); a manual re-run may upgrade it to a real verdict.
